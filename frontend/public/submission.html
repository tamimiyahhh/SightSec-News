Part A

Working Integrated System

System Overview

CyberWatch integrates three external systems through an Express.js backend deployed on Vercel: (1) the GNews REST API (gnews.io/api/v4), which supplies live cybersecurity news articles; (2) Supabase Auth, which issues and validates JWT Bearer tokens for authenticated users; and (3) Supabase PostgreSQL (with Row-Level Security), which persists user favorites. The React/Vite frontend is a separate service that communicates exclusively through the Express backend — no external API calls are made from the browser.

Source Code — Key Integration Modules

The integration logic is split across two files: server.js (Express routes, middleware, Supabase calls) and api.js (the reusable Axios client with authenticated wrappers — the Technical 3 component).

JavaScript (Express)server.js — /api/news route (IP-01 + IP-02)
// Integration Points IP-01 (Browser→Express) and IP-02 (Express→GNews)
const express   = require("express");
const cors      = require("cors");
const { fetchNews } = require("./api");  // reusable component
const { createClient } = require("@supabase/supabase-js");

const app = express();
app.use(cors());
app.use(express.json());

const CACHE_TTL = 300;  // 5-minute Vercel CDN cache

// — Auth middleware (IP-03: validates Supabase JWT) —
async function requireAuth(req, res, next) {
  const token = req.headers.authorization?.replace("Bearer ", "");
  if (!token) return res.status(401).json({ error: "Unauthorised" });
  const supabase = createClient(
    process.env.SUPABASE_URL, process.env.SUPABASE_ANON_KEY
  );
  const { data, error } = await supabase.auth.getUser(token);
  if (error || !data.user) return res.status(401).json({ error: "Invalid token" });
  req.user = data.user;
  next();
}

/**
 * GET /api/news?q=&lang=
 * Public route — no auth required; API key kept server-side only.
 */
app.get("/api/news", async (req, res) => {
  const q    = req.query.q    ?? "cybersecurity";
  const lang = req.query.lang ?? "en";

  // Input validation
  if (!/^[\w\s\-]{1,80}$/.test(q)) {
    return res.status(400).json({ error: "Invalid query" });
  }

  try {
    const articles = await fetchNews(q, lang);  // api.js
    res.set("Cache-Control", `s-maxage=${CACHE_TTL}, stale-while-revalidate=60`);
    res.json({ articles });
  } catch (err) {
    if (err.response?.status === 429) {
      return res.status(429).set("Retry-After", "60").json({ error: "Rate limit" });
    }
    if (err.code === "ECONNABORTED") {
      return res.status(504).json({ error: "Upstream timeout", fallback: true });
    }
    console.error("[/api/news]", err.message);
    res.status(500).json({ error: "Internal error" });
  }
});

/**
 * GET /api/favorites — authenticated; returns user's saved articles
 * POST /api/favorites — saves a new article to Supabase DB (IP-04 + IP-05)
 */
app.get("/api/favorites", requireAuth, async (req, res) => {
  const supabase = createClient(
    process.env.SUPABASE_URL, process.env.SUPABASE_SERVICE_KEY
  );
  const { data, error } = await supabase
    .from("favorites")
    .select("*")
    .eq("user_id", req.user.id);
  if (error) return res.status(500).json({ error });
  res.json({ favorites: data });
});

app.post("/api/favorites", requireAuth, async (req, res) => {
  const { article_url, title, source } = req.body;
  const supabase = createClient(
    process.env.SUPABASE_URL, process.env.SUPABASE_SERVICE_KEY
  );
  const { error } = await supabase
    .from("favorites")
    .insert({ user_id: req.user.id, article_url, title, source });
  if (error) return res.status(500).json({ error });
  res.status(201).json({ ok: true });
});

module.exports = app;
JavaScriptapi.js — Reusable Component (Technical 3)
/**
 * api.js — reusable HTTP client + normaliser
 * Published interface: fetchNews(), authPost(), authGet()
 * Used by: server.js (news route), any future route needing GNews or auth'd calls
 */
const axios = require("axios");

const GNEWS_BASE = "https://gnews.io/api/v4";
const API_KEY    = process.env.GNEWS_API_KEY;   // server-side only

// — GNews article normaliser —
function normalise(raw) {
  return {
    id:          raw.url,               // GNews has no article_id; use URL
    title:       raw.title       ?? "",
    description: raw.description ?? "",
    url:         raw.url         ?? "",
    image:       raw.image       ?? null,
    source:      raw.source?.name ?? "Unknown",
    publishedAt: raw.publishedAt  ?? null
  };
}

/**
 * fetchNews(query, lang) → Article[]
 * Never throws on upstream field absence — normalise() is null-safe.
 */
async function fetchNews(query = "cybersecurity", lang = "en") {
  const response = await axios.get(`${GNEWS_BASE}/search`, {
    params: { q: query, lang, token: API_KEY, max: 10 },
    timeout: 8000
  });
  return (response.data.articles ?? []).map(normalise);
}

/**
 * authGet(url, token) / authPost(url, body, token)
 * Wrappers that inject the JWT Bearer header for authenticated routes.
 */
function authGet(url, token) {
  return axios.get(url, { headers: { Authorization: `Bearer ${token}` } });
}
function authPost(url, body, token) {
  return axios.post(url, body, { headers: { Authorization: `Bearer ${token}` } });
}

module.exports = { fetchNews, authGet, authPost, normalise };

Integration Documentation

Corrected Integration Models

The integration follows a Request–Reply (synchronous) pattern between the browser and the Express API, an API Gateway pattern between Express and GNews, and a Client-SDK pattern between Express and Supabase. The original Technical 1 model had three major errors corrected below.

Divergence D-1 — Framework (Technical 1)
Proposed: Next.js 14 App Router (single monorepo, API Routes via next/server). Built: Express.js backend + Vite/React frontend as two separate services. Reason: Next.js App Router's server/client boundary created complexity for JWT session management and Supabase integration; Express gives full control over middleware ordering and token validation.
Divergence D-2 — News API provider (Technical 1)
Proposed: NewsData.io (newsdata.io/api/1, env var NEWSDATA_API_KEY). Built: GNews API (gnews.io/api/v4, env var GNEWS_API_KEY). Reason: GNews provides a cleaner JSON schema, better category filtering for cybersecurity, and a more generous free tier for the project period.
Divergence D-3 — Supabase Auth + DB not in original proposal (Technical 1)
Proposed: No authentication, no persistence. Built: Full Supabase Auth (JWT Bearer) + PostgreSQL favorites table with Row-Level Security. Reason: Requirement for a user-specific favorites feature was added after Technical 1; Supabase was chosen because its JS SDK handles both Auth and DB in one dependency.
Divergence D-4 — CSS framework (Technical 1)
Proposed: Tailwind CSS. Built: Bootstrap 5.3. Reason: Bootstrap's pre-built card and navbar components accelerated UI development; Tailwind's utility-first approach was slower for rapid prototyping given the team's existing familiarity.

Reusable Component — api.js

Divergence D-5 from Technical 3
Technical 3 identified the reusable component as a useNews React hook. The actual reusable component is api.js — an Axios HTTP client with a GNews normaliser and authenticated wrapper functions. useNews is a React UI convenience layer; api.js is the integration-layer component that could be reused by any consumer (another Express route, a CLI script, a test harness) independent of React. Technical 3 also proposed a class-based service singleton; this was rejected because a plain module with exported functions is simpler, easier to test, and avoids singleton lifecycle issues in a serverless runtime.

The api.js module encapsulates all outbound HTTP concerns: the GNews base URL and API key, the 8-second timeout, field normalisation, and authenticated wrappers. No other file knows the upstream API's field names.

authPost(url, body, token) → AxiosResponsePOST with Bearer header; used for favorites write path

Article schema (normalised output): { id, title, description, url, image, source, publishedAt }. The id field uses the article URL as a stable identifier because GNews has no article_id field (unlike NewsData.io, which the original proposal assumed).

Part D

Trends Evaluation

TrendDecisionEngineering Justification
Cloud Deployment Adopted CyberWatch is deployed on Vercel's managed cloud (serverless Node.js + CDN edge) with Supabase as a managed cloud database. This eliminates server provisioning for both compute and persistence, provides global edge presence, and auto-scales to zero — appropriate for a read-heavy, latency-sensitive news portal with unpredictable traffic. Tradeoff: vendor lock-in to Vercel's routing model and Supabase's PostgREST interface; accepted because the portability cost of multi-cloud is not justified at this scale.
Microservice Decomposition Rejected The system has two backend concerns (news aggregation, favorites CRUD), handled by a single Express app. Decomposing into separate microservices (a "news service" and a "favorites service") would introduce inter-service latency, service discovery complexity, and distributed tracing overhead. The current Express router achieves equivalent separation with named route files. If the system grew to include separate teams owning news vs. user features, decomposition would be revisited.
Containerization Rejected Vercel's serverless runtime already provides environment isolation, reproducible deploys (via lockfile), and horizontal scaling without containers. The database is externally managed (Supabase). Adding Docker would require building a custom image, managing base OS updates, and writing Compose manifests — for a system whose only runtime dependency is Node.js ≥ 18. If CyberWatch moved to a self-hosted environment or needed offline panel reproducibility, a Dockerfile would be added immediately.
Event-Driven Integration Rejected CyberWatch's news integration is inherently pull-based: articles are fetched on demand when a user loads the page; a 5-minute CDN cache satisfies the freshness requirement. The favorites write path is synchronous request–reply, appropriate for low-volume user actions. An event-driven pattern (webhook consumer, message queue) would add infrastructure with no latency or freshness benefit. It is the correct migration path if push-based alerts (notify users of new critical CVEs) are added in a future version.
API-First Design Adopted The Express routes were designed as first-class APIs before the frontend consumed them: stable URLs, documented query parameters, normalised response schemas ({ articles }, { favorites }), and consistent error envelopes ({ error: "..." }). The api.js component enforces the upstream API contract in one place. The frontend is a consumer, not a privileged internal caller. This decoupling means the React frontend could be replaced with a mobile app without touching the backend. Tradeoff: more upfront schema design; judged worthwhile because it prevents the presentation layer from reaching into integration concerns.
Part E

Case-Based Lessons

Case 1
Amazon AWS US-East-1 Outage (December 2021)
Integration failure via shared dependency on a single availability region

What happened: A cascade failure in AWS US-East-1 took down not just Amazon's own services but hundreds of dependent systems (Slack, Zoom, Netflix, IMDb) that had no cross-region failover for their integration dependencies. The root cause was a single-region dependency on internal AWS metadata service calls during automated scaling, which blocked new instance launches and triggered a widening outage. Services that consumed multiple integration points (S3, DynamoDB, Kinesis) through the same regional endpoint all failed simultaneously.

What succeeded / what failed: Services that had implemented circuit breakers and stale-cache fallbacks (e.g., Netflix's Hystrix-based resilience patterns) continued to serve degraded but functional content. Services relying on synchronous, no-timeout integration calls to US-East-1 became completely unresponsive.

Design Change Produced in CyberWatch
Cache-Control + stale-while-revalidate. The AWS case directly motivated the IP-05 Vercel CDN integration with s-maxage=300, stale-while-revalidate=60. When GNews is unreachable, the CDN continues serving the last cached response for up to 60 seconds while attempting revalidation in the background. Without this, every user request would propagate the upstream failure immediately. The "fallback":true field in the 504 response was also added so the client can display a "showing cached results" banner rather than a blank screen. Additionally, the 8-second timeout in api.js ensures the serverless function does not hang for Vercel's full execution limit.
Case 2
Optus API Key Exposure (2022 Data Breach)
Integration security failure: unauthenticated API endpoint exposed after migration

What happened: Optus, Australia's second-largest telco, suffered a breach affecting 9.8 million customers when an internal customer API — originally protected by authentication — was inadvertently exposed to the public internet without any authentication gate following a network migration. An attacker discovered the endpoint, iterated over sequential customer IDs, and exfiltrated names, dates of birth, and identity document numbers. No rate limiting, no authentication, and no anomaly detection were in place.

What succeeded / what failed: The API itself was well-structured and functional. The integration security layer — authentication, authorization, and monitoring — had been silently removed during a migration and never verified post-deployment. The integration worked as designed; the security model around it failed completely.

Design Change Produced in CyberWatch
Three concrete controls. (1) API key stored server-side only: GNEWS_API_KEY and both Supabase keys are sourced from process.env in api.js and server.js; they are never referenced in any frontend file or exposed in the client bundle. (2) requireAuth middleware verified post-deployment: After the Optus case's lesson that security controls must be verified after every migration, the favorites routes were manually tested with expired and absent tokens after each Vercel deployment, not just during development. (3) Input validation on the query parameter: The q parameter is regex-validated before being forwarded to GNews, preventing parameter injection. These controls are reflected in the IP-01, IP-02, IP-03, and IP-04 rows of the security assessment (Part C.3).
